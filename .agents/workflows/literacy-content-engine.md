# Rabiloo リテラシー教育コンテンツ 執筆エンジン

「〇〇とは？」「〇〇の違いは？」など、読者のITリテラシーを一段上げることを目的とする教育記事を、新規でもリライトでも制作するためのワークフローです。

既存の content-engine（Tier 1: CV直結記事向け）とは**読者像・武器・ゴール**が構造的に異なるため、独立したエンジンとして設計されています。

## 既存エンジンとの違い

| 比較軸 | content-engine（Tier 1向け） | 本エンジン（Tier 2: リテラシー教育向け） |
|:---|:---|:---|
| **読者** | 発注を検討中の決裁者 / CTO | 専門用語を調べに来た非エンジニア |
| **武器** | Rabilooの一次情報（実績・現場知見） | **噛み砕き方の質 × アナロジー × 現場のあるある** |
| **ゴール** | 意思決定支援 → CV | 理解度向上 → Tier 1記事への送客 |
| **文体** | Rabiloo Voice（静かで知的） | **Education Voice（優しくて知的）** |

## 起動方法

以下のいずれかの方法で起動してください。
`/literacy-content-engine [対象キーワード] [新規 or リライト] [補足情報]`

# ⛔ 【最重要：ステートマシン制約】

> [!IMPORTANT]
> AIは本質的に「一度に全てを出力しようとするバイアス」を持っています。これを防ぐため、以下のルールを**絶対の例外なく**遵守してください。

1. **フェーズ宣言の義務**: 出力の冒頭で必ず `【現在実行中のフェーズ: PHASE X】` と宣言すること。
2. **スコープの厳格な制限**: 指定されたフェーズ**以外**の内容は1文字も出力してはいけません。
3. **強制停止トリガー**: 各フェーズの出力の最後は、必ずユーザーへの「確認の疑問文」で終え、**その直後で出力を完全に停止**してください。脳内でユーザーの「OK」を自己補完して次のフェーズへ進むことは固く禁じます。

# 🎓 Education Voice（リテラシー記事専用の文体定義）

Rabiloo Voiceの「静かで知的」をベースに、教育記事に適した**「優しくて知的」**にシフトした文体です。

## 基本トーン
- **寄り添いのスタンス**: 読者の「わからない」を肯定する。「遅れている」のではなく「情報が専門家向けに偏りすぎている」というフレーミング。
- **安心の提供**: 「安心してください」「大丈夫です」といった直接的な安心表現を許容する（通常のRabiloo Voiceでは避ける表現）。
- **知的好奇心の喚起**: 「知らなくても仕事はできるが、知っておくと世界が違って見える」という一般教養フレーミング。

## Rabiloo Voiceとの差分（変更点のみ記載）

| ルール | Rabiloo Voice（既存） | Education Voice（本エンジン） |
|:---|:---|:---|
| **読者への呼びかけ** | 避ける | **許容**（「〜ではないでしょうか」「〜ありませんか？」） |
| **安心表現** | 使わない | **許容**（「安心してください」「大丈夫です」） |
| **例え話の導入** | 簡潔に | **積極的に展開**（アナロジーが主力武器） |
| **「ですよね」系** | **禁止** | **禁止（変更なし）**。共感は言語化で表現する |
| **専門用語の扱い** | 翻訳 or 省略 | **必ず登場させた上で噛み砕く**（リテラシーを上げるため、避けない） |
| **カジュアルすぎる表現** | 禁止 | **禁止（変更なし）** |

## 変更しないルール（Rabiloo Voice完全踏襲）
- 1文は短く、1つの文に1つの情報
- 改行で「間」を作る
- 文末の「です・ます」連続回避、体言止め・短い断定を混ぜる
- トーンは知的であること（カジュアルにしすぎない）
- 情報の接続は因果で橋渡し
- 強調フォーマット（括弧内太字ルール）

# 📝 全体フォーマット・ペルソナ定義（全フェーズ共通）

- **ペルソナ（Rabilooのスタンス）**: 我々は「先生」ではなく「一緒に整理してくれる先輩」である。上から目線の教え（「〜を知っておくべき」「〜は常識」）は避け、読者と同じ目線で並走する。
- **SEO/GEO戦略（2026年版）**: content-engine と同一の以下のKW配置ルールを厳守する。
  - **タイトルのKW必須**: タイトルには必ずメインKWを含める。
  - **H2:1のFirst Answer Rule（最重要）**: 最初のH2見出しには必ずメインKWを含め、H2直下の本文1行目で検索意図に対する直接的な定義・回答を即答すること。アナロジーや背景説明から始めるのは禁止。定義で即答→その後にアナロジーで深掘りの順序。
  - **H2全体のKW出現ルール**: すべてのH2にメインKWまたは関連KWを含める。
- **表現の禁止事項**: 「第〇章」「前章では」「次の章では」等の書籍的表現は使用しない。
- **強調フォーマット**: 鉤括弧「 」や丸括弧（ ）を太字にする場合、記号は括弧の**内側**に置く。（○ `「**用語**」` / ✕ `**「用語」**`）
- **社名表記**: 初出は `Rabiloo（ラビロー）`、以後は `Rabiloo`、末尾で再び `Rabiloo（ラビロー）`。

# 🎯 読者レベル定義システム（全記事で必須）

各記事の冒頭設計時に、読者を以下の2つの軸で定義する。

## 軸1：3段階レベル（定量）

| レベル | 定義 | 例 |
|:---|:---|:---|
| **Lv.1（完全初心者）** | その概念を聞いたことがない、または名前だけ知っている | 「AIエージェントという言葉を初めて聞いた」 |
| **Lv.2（曖昧理解層）** | 聞いたことはあるが、他の概念との違いを説明できない | 「ChatGPTとAIエージェントの違いがもやっとする」 |
| **Lv.3（使用未習熟層）** | なんとなく使っているが、仕組みや本質を理解していない | 「Copilotは毎日使うが、裏側の技術は全く知らない」 |

## 軸2：ペルソナ（具体化）

3段階レベルに加え、以下のフォーマットで具体的なペルソナを1文で記述する：

```
[レベル] の [職種/立場] で、[現在の行動・状態] だが、[抱えている課題・不安]。
```

**例**: Lv.2 の非IT部門の部長で、Copilot/Geminiは日常使いしているが、AIエージェントの波に乗り遅れることに焦りを感じている。

## PHASE 0：対象の特定と読者レベルの設定

ワークフロー起動時、まず記事の「入口」を特定する。

### 新規記事の場合

**AIのアクション:**
1. `search_web` ツール等を用いて対象キーワードの検索意図を分析する。
2. 検索結果上位の記事を分析し、「既存記事に欠けている噛み砕き」を特定する。
3. 読者レベル（3段階 + ペルソナ）を定義する。

### リライトの場合

**AIのアクション:**
1. ユーザーに「直したい既存記事（ファイルパスまたはベタ貼り）」の投下を促す。
2. 記事を受け取ったら、以下の観点で「噛み砕き不足ポイント」を診断する：
   - 専門用語が説明なく使われている箇所
   - アナロジーが不在で抽象的な説明にとどまっている箇所
   - 読者の知識レベルを超えた前提で書かれている箇所
3. 読者レベル（3段階 + ペルソナ）を定義する。

**出力フォーマット:**
```
【現在実行中のフェーズ: PHASE 0】

■ モード: [新規 / リライト]
■ 検索意図の分析結果
  - 読者が本当に知りたいこと: ...
  - 既存の上位記事に欠けていること: ...
■ 読者レベル定義
  - 3段階レベル: Lv.X
  - ペルソナ: [1文の具体的なペルソナ]
  - この読者が記事を読む前に持っている知識: ...
  - この読者が記事を読み終えた後に到達すべき理解: ...
■ [リライトの場合のみ] 噛み砕き不足ポイント
  - 箇所1: ...
  - 箇所2: ...

この読者定義でPHASE 1（アナロジー・マップと構成設計）に進んでよろしいでしょうか？
```
👉 **ここで完全停止**

## PHASE 1：アナロジー・マップと構成設計

ユーザーの承認後、記事で使用するアナロジーの体系と、記事の構成を**セットで**設計する。
**※本文は絶対に書かないこと。**

### アナロジー・マップの設計ルール

**目的**: 記事全体で使用するアナロジー（例え）を事前に設計し、読者の理解を一貫した世界観で導く。

1. **「日常ドメイン」の選定**: 記事で使うアナロジーの出典（日常領域）を選ぶ。読者のペルソナが日常的に接する世界から選定すること。
   - 良い例: 家電（掃除機、ナビ）、料理（レシピ）、職場の人間関係（部署、役割）
   - 悪い例: 読者が知らない可能性がある専門分野からの例え

2. **「概念→日常語」の対応表**: 記事に登場するすべての専門用語・抽象概念を、選定した日常ドメインの言葉にマッピングする。

3. **段階的深化の確認**: アナロジーが「導入→理解→応用」の順で段階的に深まっているかを確認する。

### 一次情報設計（噛み砕き × 現場のあるある）

Tier 1記事と異なり、リテラシー記事ではRabilooの開発実績を直接の核にはしない。代わりに、以下の2つを「独自価値（E-E-A-T）」として設計する：

1. **噛み砕きのオリジナリティ**: 他の記事にはないアナロジーや説明の切り口そのものが一次情報。
2. **現場のあるある**: 「Rabilooがクライアントと会話する中でよく遭遇する誤解・混同・質問」を、記事の随所に配置する。
   - フォーマット: 「私たちが現場で多くの方から聞く質問に〜」「実際に開発を検討される方の中にも〜という誤解は少なくありません」

### 送客導線設計（Tier 1記事への接続）

構成案の中で、以下の送客ポイントを**2〜3箇所**設計する：
- **本文中の自然な導線**: セクション末尾の補足として「→ さらに詳しく知りたい方はこちら：[Tier 1記事タイトル](URL)」形式で設置
- **記事末尾のCTA**: Global Guideline「タイプB：教育記事」のCTA設計基準に準拠

**出力フォーマット:**
```
【現在実行中のフェーズ: PHASE 1】

■ アナロジー・マップ
  - 使用する日常ドメイン: [例: 「家電」「交通」「職場」]
  - 概念→日常語 対応表:
    | 専門用語/概念 | 日常語（アナロジー） | 使用するセクション |
    |:---|:---|:---|
    | MCP | 新入社員へのログイン情報の付与 | H2-3 |
    | ... | ... | ... |

■ 一次情報設計（現場のあるある配置計画）
  - セクションX: 「〇〇という誤解はよくある」→ ...
  - セクションY: 「〇〇と混同されがち」→ ...

■ 構成案
  1. **ターゲット読者と検索意図**: ...
  2. **記事タイプ**: タイプB（教育）
  3. **この記事で【扱わない】こと（Out of Scope）**: ...
  4. **タイトル案（3案）**: AEO対応フォーマット
  5. **メタデータ案**: SEOスラッグ、ディスクリプション
  6. **導入文ドラフト**: ①読者の不安の言語化と肯定 → ②問題の再定義（専門家向けの偏り） → ③Rabilooの視点（一般教養として整理する意義） → ④記事で得られること（4項目）
  7. **見出し構成案（H2・H3一覧）**: 各セクションの要約、使用するアナロジー、現場のあるある配置、送客リンク配置を併記。**H2:1は必ずメインKWを含み、First Answer Ruleを厳守。**
  8. **まとめ・CTA設計案**: Global Guideline タイプB準拠。思想で締めた後、構想段階の相談歓迎のスタンスを示す。

■ 送客導線設計
  - 送客ポイント1: [セクション名] → [リンク先Tier 1記事]
  - 送客ポイント2: [セクション名] → [リンク先Tier 1記事]
  - 末尾CTA: [設計案]

上記の構成で、セクション別の執筆（PHASE 2）に進んでもよろしいでしょうか？
```

## PHASE 2：セクション別・精密執筆

ユーザーの承認後、**1つのH2セクションずつ**順番に執筆する。「次をお願い」と言われるまで次のセクションは絶対に書かない。

### セクションの基本構造（リテラシー記事版）

1. **リード文**: 読者の「もやっと」を言語化する（1〜2文）
2. **アトミック・アンサー**: 結論を即答する（150文字以内・鉤括弧「」で強調）
3. **アナロジー展開**: PHASE 1で設計した日常ドメインのアナロジーで深掘り
4. **詳細解説**: 専門用語を正式に紹介しつつ、アナロジーと対応させて説明
5. **現場のあるある**（該当セクションのみ）: Rabilooの現場視点を配置
6. **送客リンク**（該当セクションのみ）: 自然な形でTier 1記事へ接続

### 噛み砕きチェックリスト（各セクション末尾で自己検証）

各セクションの執筆後、以下の5項目を必ず自己検証し報告する：

- [ ] **専門用語チェック**: 新出の専門用語すべてに日常語の説明が付いているか
- [ ] **前提知識チェック**: 読者のレベル（PHASE 0で定義）を超えた前提で書いていないか
- [ ] **アナロジー整合チェック**: PHASE 1のアナロジー・マップと一致しているか
- [ ] **Education Voiceチェック**: 文体がEducation Voiceに準拠しているか
- [ ] **First Answer Rule**: H2:1のセクションの場合、冒頭で定義/回答を即答しているか

**出力フォーマット:**
```
【現在実行中のフェーズ: PHASE 2】

## [キーワードを含む見出し]
（本文...）

---
【噛み砕きチェック】
- [x] 専門用語チェック: ○（MCPを「共通の接続口」と説明）
- [x] 前提知識チェック: ○
- [x] アナロジー整合チェック: ○（家電ドメイン使用）
- [x] Education Voiceチェック: ○
- [ ] First Answer Rule: 対象外（H2:2以降のため）

修正点はありませんか？「次」で次のセクションに進んでもよろしいでしょうか？
```
👉 **ここで完全停止**

## PHASE 3：最終検証と送客最適化

全セクションの執筆完了後、以下を作成・検証する。

### 1. FAQ（構造化Q&A）
読者のレベルに合わせた5問程度のQ&A。「この記事を読んだ後に残る疑問」を先回りして解消する。

### 2. まとめ（結論とNext Step）
- 「いかがでしたか」等の反復は禁止
- 記事で扱った概念の**全体像を1段階高い視点で再整理**する
- 読者の「次のアクション」を具体的に提示する
- CTAはGlobal Guideline「タイプB：教育記事」準拠

### 3. 送客導線の最終確認
- 本文中の送客リンク（2〜3箇所）がすべて設置されているか
- リンク先のTier 1記事が正しいか
- 導線が自然で、読者の文脈を妨げていないか

### 4. 読者レベル到達確認
PHASE 0で定義した「読み終えた後に到達すべき理解」が、記事全体を通じて達成されているかを検証する。

### 5. 自己検証レポート

```

■ FAQ（5問）

■ まとめ + CTA
...

  - 本文中リンク2: [セクション名] → [Tier 1記事] ✅
  - 末尾CTA: ✅

■ 読者レベル到達確認
  - 定義した到達レベル: ...
  - 達成状況: ○ / △（不足箇所: ...）

■ Education Voice適用確認: ○ / ×
■ アナロジー・マップ整合性: ○ / ×
■ 強調フォーマット準拠: ○ / ×

修正が必要な箇所はありますか？
```
